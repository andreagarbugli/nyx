# Chapter 0.5 — Decisions to make before the first line

*Written after building the thing once. Everything here is a rule that
cost real time to learn, and every one of them is cheap to adopt on day
one and expensive to retrofit.*

---

## Why this chapter exists

The rest of this book is ordered for **learning**: mechanism first, then
the hard parts, then concurrency, then the verticals. That order is
right for understanding and wrong for building, in a specific and
narrow way. A handful of decisions look like local implementation
choices when you meet them in chapter 5 or 7, and turn out to be
properties of every data structure you have written by chapter 12.

There are seven. Adopting them costs a few hours at the start. Not
adopting them cost, in the reference implementation:

- three separate bugs in one commit, all "per-CPU state that looked like
  machine state" (chapter 12 §2);
- a latent self-deadlock that never fired and was found by a
  measurement, not by review (chapter 12 §4.2);
- a scheduler whose runqueue became per-CPU only after SMP already
  worked, because it had been written when "the CPU" was a definite
  article;
- two independent client/server pairs scaling at **1.20×** rather than
  2× on four processors.

None of those was a mistake in the sense of "someone wrote the wrong
line". Each was a structure that had been correct for one processor and
was silently wrong for four.

> **A note on how to read the rest of the book after this.** Nothing
> below contradicts a later chapter's *mechanism*. Where it contradicts
> a later chapter's *ordering* — and it does, twice, in chapters 9 and
> 12 — this chapter is the correction, and the chapter says so at the
> point of disagreement.

## 1. Design partitioned, even while you write a uniprocessor

Chapter 12 §1 lays out the honest staged plan: design as if partitioned,
add a big kernel lock so the APs can run at all, then remove the lock
path by path with measurements. The reference implementation did steps
two and three and skipped step one, because step one does not feel like
work when there is one CPU.

**The rule:** every kernel structure is either per-CPU or explicitly
shared with a named owner and a lock rank — from the first commit. There
is no `static struct foo foos[N]` without a CPU index or a rank beside
it.

You are not writing locks yet. You are writing the *shape* that lets
locks be added one at a time later:

```c
/* Day one, on a machine with one processor. */
static struct runqueue rq[NCPU];        /* not: static struct runqueue rq; */
static struct cpu      cpus[NCPU];      /* not: three loose globals        */
#define this_rq() (&rq[this_cpu()->id])
```

`NCPU` is 1 today. The cost is one array index. The alternative is
finding, later, that `current`, the runqueue, the TCB pool, the trace
ring and the IRQ counters are all global *for the same reason* and all
have to move *at the same time* — which is exactly the change you do not
want to be making while you are also debugging a real-mode trampoline.

**What "per-CPU" has to mean mechanically:** the CPU that owns the data
is the only one that writes it. If a structure needs a lock to be
per-CPU, it is not per-CPU data; it is shared data with an optimistic
access pattern, and it should carry a rank.

## 2. One `cpu_init()`, and every processor runs it

The boot stub sets up the processor it is running on. That is
unavoidable and it is fine. What is not fine is *leaving it there*,
because every register it sets is per-CPU state that an application
processor will not have.

In the reference implementation this produced three bugs in a single
commit, none of which was visible by reading the code that broke:

| Missing on the AP | What it looks like |
|---|---|
| `EFER.SCE` | `syscall` is `#UD` — an invalid opcode at a perfectly valid instruction, which reads as memory corruption |
| `CR0.WP`, `CR4.SMEP`/`SMAP`/`UMIP` | the kernel's own protections silently absent on 3 of 4 processors |
| `CR4.PGE` | that processor flushes more than it needs to, silently, forever |

**The rule:** there is exactly one function that puts a processor into
the state the kernel expects, and the BSP calls it too — immediately
after the boot stub hands over, before anything else. An AP's bring-up
path calls the same function and nothing else.

```c
void cpu_init(unsigned index, uint32_t apic_id)   /* every CPU, BSP included */
{
    percpu_init(index, apic_id);   /* GS first: everything below needs it */
    gdt_load_this_cpu(index);      /* own TSS, own IST stacks */
    idt_load();                    /* shared table, per-CPU register */
    lapic_init();                  /* per-CPU SVR/TPR/enable */
    vmm_harden_this_cpu();         /* CR0.WP, CR4.SMEP/SMAP/UMIP/PGE */
    syscall_init();                /* EFER.SCE, STAR/LSTAR/FMASK */
}
```

Write this function in chapter 3, when it has one caller. The day you
add the second caller, you are done — instead of spending an afternoon
discovering which of forty control-register bits the second processor
never got.

**Corollary, and it is the general form of the rule:** any time you
write "the CPU", ask whether you mean *this* CPU or *every* CPU. The
bugs live where those two readings differ and the code cannot tell.

## 3. Never let one fact have two representations

Every expensive bug that was not category 1 or 2 was this: a constant, a
layout, or an invariant that existed in two places and drifted.

Real examples, all of them from a codebase whose author knew better:

- a syscall number in an ABI header and in an assembly `%define`;
- struct offsets in `percpu.h` and in `percpu.inc`, because the entry
  stub cannot include a C header;
- a slot layout in an enum and in the loop that filled the slots;
- an enum value inserted mid-list, renumbering everything after it,
  while a second copy still said the old number.

**The rule:** a fact lives in one place. Where the language forces a
second copy — assembly needs constants a C header cannot give it — the
copy is *mechanically checked*, not carefully maintained:

```c
/* include/nyx/percpu.h */
#define CPU_KERNEL_RSP 0
_Static_assert(offsetof(struct cpu, kernel_rsp) == CPU_KERNEL_RSP, "");
```

and the assembly `%include`s a file whose only job is to hold the same
numbers, with a comment saying what asserts them. If you cannot check
it mechanically, arrange for a *test to read the value through the other
copy*, so a mismatch is a wrong answer rather than a silent divergence.

**Enums that cross a boundary are append-only, forever.** Not because
renumbering is philosophically wrong, but because the second copy of the
enum is in a binary you are not rebuilding right now.

## 4. Make every obligation symmetric, or do not create it

When object A points at object B to record a relationship — "this thread
owes that thread a reply", "this thread is queued on that endpoint" —
you have created an obligation with two ends. Destroying *either* end
must cancel it.

The reference implementation got this right once and wrong once, in the
same pair of pointers. Killing the *server* released the client. Killing
the *client* left the server holding a pointer to a destroyed thread,
and its next reply resumed whatever now occupied that slot. The window
had existed for four milestones; nothing had exercised it, because the
chaos test killed servers and not clients.

**The rule:** when you write `a->x = b`, ask what happens when `b` dies.
If the answer requires a search, add the back pointer. Then write *both*
teardown paths in the same commit, and a test for each. An invariant
enforced in one direction is not an invariant; it is a comment that
happens to be true so far.

The same rule, in the object model: a refcount that says "this object
lives while a capability names it" must be honoured by *everything* that
recycles storage — including, in the reference implementation, a thread
slot allocator that checked liveness by state and not by refcount, and
so handed out a TCB that a capability still pointed at.

## 5. Measure before you optimise, and audit the measurement first

Chapter 33 covers this properly. Two things belong here because they
change what you build on day one:

**Numbers are a deliverable, so the harness is part of the kernel.**
Build the benchmark runner and the in-kernel test suite in chapter 2,
not chapter 18. Everything after that gets a number attached for free,
and "is this faster" stops being a discussion.

**Audit the instrument before believing it.** The reference
implementation pinned its benchmarks to core 0 to reduce noise. On the
machine in question, core 0 is where the host's housekeeping and
interrupts live: the pin *was* the noise, worth 30% on a null syscall
and enormous variance. It went unnoticed for four milestones because
nobody asked the harness to justify itself.

Three specific traps, all of which produced wrong numbers for a while:

- **A `rdtsc` under emulation is not a cycle.** Under TCG it counts
  interpreter steps. Any cycle budget must skip, not pass, when the
  emulator is in charge.
- **You cannot measure a worst case inside a VM.** The host can
  deschedule a vCPU inside a critical section that has interrupts
  disabled, and from inside the guest that is indistinguishable from
  your own code taking that long. Report a max; *assert* on something
  robust — a percentile if you have thousands of samples, a share-over-
  budget if you have hundreds.
- **A measurement that spans a context switch measures the wrong thing.**
  "How long was this syscall non-preemptible" is not "how long from
  entry to exit"; a syscall that blocks is descheduled inside its own
  region. Bank the region into the thread, not the CPU.

## 6. Decide the transport and the object representation once

Two decisions are near-impossible to change later because every protocol
and every file inherits them.

**The IPC transport.** Decide the message shape against a workload, not
against a register budget. The reference implementation carried four
register words, then bolted capability transfer into the high bits of
the syscall number register because there was nowhere else to put it —
and every protocol above it inherited a 32-byte ceiling. Its ramdisk
serves a 4 KiB page in **128 round trips**. A per-thread IPC buffer
decided on day one (chapter 8 §6a) makes capability transfer, long
messages and bulk descriptors one mechanism instead of three; the
register fast path then becomes an *optimisation of* that shape rather
than the shape itself.

**The capability representation.** Chapter 9's packed 16-byte capability
is a performance decision that looks deferrable and is not: unpacking
later is free, packing later touches every file that names a field. The
reference implementation's `struct cap` is 56 bytes with CDT pointers,
and its capability lookup measures 43 cycles against the 5–20 this book
predicts — a gap entirely explained by the representation.

Same argument, smaller: **a reply is an object, not a pointer.** If you
store "who I owe a reply to" as a raw TCB pointer, you will write §4's
back pointer eventually. A Reply capability can be held, transferred to
a worker, and revoked, and its lifetime is the CDT's problem rather than
two pointers you must keep symmetric by hand.

## 7. Long operations are preemptible from the first one you write

Chapter 14 §6.2 lists the kernel operations with no bound: revocation
walks a subtree of unknown size, retyping zeroes O(size) bytes, address
space teardown is O(mappings). Chapter 9 §3 gives the fix — store
progress in the object, return a restart code, let userspace re-invoke.

**Write them that way immediately.** Not because you need the real-time
property on day one, but because the shape is contagious in the wrong
direction: every caller written against "this completes" has to be found
and changed when it stops completing. In the reference implementation
that meant the root task, the process manager and the reincarnation
server all learned to loop, after the fact.

The measured cost of not doing so: `Untyped_Retype`'s zeroing was the
largest non-preemptible region in the system by an order of magnitude —
200 µs at p99.9 — and no deadline shorter than about 250 µs could be
honoured on any processor where a component might allocate.

## The checklist

Before the first line:

- [ ] `NCPU`, `this_cpu()`, and every kernel structure indexed or ranked
- [ ] one `cpu_init()`, called by the BSP as well
- [ ] every duplicated constant `_Static_assert`ed or read back by a test
- [ ] enums that cross a boundary marked append-only
- [ ] test harness and benchmark runner exist and are wired to `make`
- [ ] the IPC message shape decided against a workload and written down
- [ ] capability representation decided (packed or not) and written down
- [ ] a rule that every obligation gets both teardown paths in one commit
- [ ] a rule that long operations return a restart code

None of that is a large amount of code. All of it is structure, and
structure is the thing you cannot add later without touching everything
at once.

---

## What this chapter is not

It is not a claim that the rest of the book's ordering is wrong. Chapter
12's staged plan for removing a big kernel lock is right, and you will
still write the lock. What changes is that the structures it protects
were *already shaped* to come out from under it, one path at a time,
instead of all at once.

Nor is it a substitute for building the thing badly once. Most of these
rules are obvious when stated and were not obvious when needed. If you
are reading this before your first kernel, take them on faith and cheaply.
If you are reading it after, you already have your own list — and the
useful exercise is to compare the two.
